## 执行步骤

1. 使用 `get_current_time` 获取当前时间，作为后续日志查询的时间范围基准
2. 使用 `query_logs` 查询系统日志：地域 `ap-guangzhou`，日志主题 `system-metrics`，时间范围最近 30 分钟，查询条件 `level:ERROR OR cpu_usage:>80`；若 `query_logs` 工具不可用，改用 MCP 提供的日志查询工具
3. 从日志结果中定位 CPU 消耗进程：进程名称和 PID、CPU 占用百分比、进程启动时间、进程所属服务
4. 使用 `query_logs` 查询应用日志：地域 `ap-guangzhou`，日志主题 `application-logs`，时间范围与告警时间一致，查询条件 `level:ERROR OR level:WARN`
5. 综合日志证据，对照「常见原因分析」章节判断根因类型，并给出对应的处理方案
6. 生成诊断报告，包含告警信息、证据、根因结论和处理建议

## 常见原因分析

- **死循环或无限递归**：单进程 CPU 接近 100%，应用日志有大量重复错误堆栈，内存可能同步增长。处理：立即重启受影响的服务实例 → 查看应用日志定位代码问题 → 回滚到上一个稳定版本 → 通知开发团队修复
- **流量突增**：多进程 CPU 均匀升高，请求量明显增加，响应时间变长但无明显错误。处理：检查是否有营销活动或突发流量 → 启动自动扩容机制 → 恶意流量启用限流策略 → 监控扩容后的 CPU 使用率
- **定时任务重叠执行**：CPU 周期性升高，特定时间点出现，日志中有定时任务执行记录。处理：检查定时任务配置 → 调整任务执行时间避免重叠 → 优化任务执行逻辑 → 增加任务执行互斥锁
- **数据库查询慢**：应用 CPU 高但业务逻辑简单，日志中有慢查询记录，数据库连接池占用高。处理：查询慢 SQL 日志 → 优化 SQL 语句或添加索引 → 检查是否有全表扫描 → 考虑增加缓存层

## 验证步骤

1. 确认 CPU 使用率降到正常水平（<60%）
2. 检查应用响应时间恢复正常
3. 确认无新的错误日志产生
4. 观察 30 分钟确保问题不再复现
